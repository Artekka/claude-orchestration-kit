# Worked example — one orchestrator, three siblings, twelve hours

A real annotated session. One Claude session held the **orchestrator seat**; three sibling
Claude sessions built in isolated git worktrees. Nine rows shipped across **two deploy
trains**, two rows were killed on evidence, a live production data bug was found and fixed,
and a test suite that had been red for **37 days** was discovered.

Names are the kit's: the seat is the orchestrator, `Sib1/2/3` are builders, row IDs carry the
seat's per-session prefix (`ORCE-*`). Nothing here is hypothetical — the failures are the
point, and most of them are the seat's.

---

## 0 · Taking the seat

The seat starts by orienting, then claims the board with a banner naming itself, its row
prefix, the resume state it **verified rather than inherited**, and the standing rules.

The very first thing that happened is the reason `/orient` exists:

> The handover banner said a milestone log entry was still owed, with a draft sitting
> uncommitted in a worktree. **Sib1 checked and it had landed the day before.** The seat
> verified independently: the commit was on main, the entry was in the log, and the
> worktree draft would have appended a **second copy of the same heading** to a
> 33,000-line append-only file.

**A handover banner's resume state is a hypothesis like any board row.** Verify it before
acting on it. That check cost ninety seconds and saved a corrupted history.

---

## 1 · Distributing work

Three siblings came online within two minutes of each other. The seat woke each with the
same handshake — orient first, report your session ref, then stand by — and had briefs ready
before they finished orienting.

**Work came from four intakes**, which is what keeps three builders busy without inventing
make-work:

| Intake | Became |
|---|---|
| An inherited open row from the previous seat | `S2-1` (CSS single-sourcing) |
| The project's own task board | `ORCE-2` (a dead click in the guild UI) |
| A **player's bug report** in the community queue | `ORCE-1` → `ORCE-5/7/8` |
| Verifier findings from work already in flight | `ORCE-9`, `ORCE-15`, `ORCE-24`, `ORCE-25` |

That last row is the engine of a long session: **most of the second half's work was
generated by verification of the first half's.**

### Fences are checked before assignment, not after

Three builders in one repo only works if their file fences are provably disjoint. The seat
assigned:

- **Sib1** → `index.css` + the Tailwind config
- **Sib2** → read-only in the combat engine
- **Sib3** → the guild hall page

and told each one explicitly what the other two held. Later, when two rows both needed the
4,600-line reference page, the seat fenced them to **one paragraph each** — and the eventual
merge auto-resolved cleanly, which is the fence design working rather than luck.

### A brief is a hypothesis, and says so

Every brief ended with an instruction to correct it upward. This paid out repeatedly — and
the sharpest instance was against the seat itself:

> The seat wrote a row from a sibling's closing suggestion **without checking a line of
> code**. Sib3 found the premise was false: the field the brief claimed was rendered
> appears nowhere in the client. It then found the *real* defect nearby — two figures about
> the same quantity, ~95 lines apart, measured against the same threshold, one a current
> value and one a lifetime total, with nothing distinguishing them.

The seat's error is recorded on the board as the seat's. **An orchestrator that writes an
unverified premise into an assignment has done the exact thing it warns builders about.**

## 2 · Checking in

Builders report at TDD phase boundaries — claimed → RED → GREEN + self-gate — and the seat
answers design questions rather than polling for status.

**The check-ins that mattered were the ones where a sibling stopped and asked:**

- Sib3 traced a row's seam, proposed a fence, and asked two scoping questions **before
  building**. One answer ("instructor-only, don't generalise") kept the row small; the other
  approved a shared message builder.
- Sib2 hit a design fork inside an engine change — a documented guard had become
  *uncomputable* under the new ordering — and asked before deleting it. That became a spec
  revision with the reasoning recorded, not a silent removal.
- Sib1 found that the two code copies it had been asked to merge were **not identical**, and
  rather than pick a winner, made the difference an explicit required parameter so neither
  caller's behaviour moved.

The seat's job at each of these was to **rule, record the ruling, and say why** — so the next
reader meets the argument and not just the outcome.

### Escalating to the human

Four design forks went to the project owner in batched multiple-choice questions, not one at
a time. One answer overrode the options offered entirely ("max fielded units is 10 ever"),
which **superseded an earlier answer in the same session** — the seat took the later, narrower
statement literally rather than mapping it onto the nearest option, and closed the item as
working-as-intended instead of opening work.

**When an answer doesn't match the options, it is a correction of the question.**

---

## 3 · Verification at every hand-off

Every finished row went to an independent verifier that received **the contract and the diff
only** — never the builder's reasoning. Verdicts today: several `PASS`, and five `DEVIATES`
that each found something a green test suite could not.

What the verifiers caught, all on green trees:

- **A warning that never appeared on the device the reporter used.** The feature worked
  everywhere except one screen size — where a different component is substituted. All six of
  its tests rendered the component *directly*. **A component test cannot see a regime that
  never mounts the component.**
- **Six decisions revertible to a hardcoded value with all 2,319 combat tests still green.**
  Zero coverage existed for the state combination in question.
- **A replay that reconstructed 20 HP where the live battle gave 17** — and the existing
  parity guard stayed green through it, because its fixture happened to be
  order-*insensitive*. Coverage that cannot fail on the defect it appears to cover.
- **Eight fields already missing** from a type, where the row had asked to stop *one* from
  being dropped. The data arrived at runtime; only the type declaration stopped any renderer
  from reading it.
- **An entire guard family blind to type drift.** Flipping a field's type in the canonical
  schema left the dedicated drift guard green at 47/47.

**A `DEVIATES → roundtrip → delta-PASS` arc is the system working.** The seat re-verified as a
*delta* against the previously-verified SHA rather than paying for a full pass each time.

### When roundtrips stop converging, change the method

One row took **three** comment-cleanup rounds — 2 named/9 found, 6 named/6 fixed, then 11
more. The seat stopped asking for a fourth sweep and demanded an **enumeration**: a fixed
term list, run repo-wide, **with a written verdict per hit**, before fixing anything.

Result: 396 raw hits → 157 candidates → 13 genuinely false, including two the seat had never
named. The builder's own diagnosis of why sweeping failed is the better one:

> "A term-sweep returns mostly noise, so the reader filters by *plausibility* — and a hit in
> a file that looks like someone else's area gets skipped. **The filter, not the search, is
> what drops them.** Typing a verdict per hit makes 'unrelated' a decision rather than an
> omission."

## 4 · Ingesting from worktrees and merging

Builders never merge and never deploy. The seat reconciles **one row at a time**:

```bash
# from the SHARED checkout, never from inside a worktree
git merge --no-ff origin/<builder-branch> -m "<why, in plain language>"
git push origin main
git branch -r --contains <builder-sha> | grep -c origin/main   # ← verify, don't trust
```

That last line is not ceremony. **Pushing from inside a worktree is a silent no-op** — it
pushes that worktree's stale local `main` ref, reports success, and the commit never leaves
its branch. It bit the seat **twice**, both times caught only by re-reading the remote.

Stacked rows merge in dependency order. When one row's guard asserted the holes another row
had just closed, the builder correctly branched off that row's tip rather than main — a
main-based branch could not have been green without weakening the guard.

### The combination gate

Rows verified separately are not proof they are green together. Before any deploy the seat
gates the merged result — foreground, unpiped, from a worktree whose echoed SHA it reads:

```
✅ GATE GREEN [<worktree> — <branch> @ <sha>]
goldens 124/2546 · client 3324 · DOM 2272 · server 585+1 · bot 385
```

Counts are cross-checked against each builder's stated delta. Today every one tied out
exactly — and where a count *looked* wrong (a builder's client count 19 below main's), the
verifier established it was a stale base rather than a regression.

## 5 · Deploying a wave train

A train is 1–3 rows that finished together. The seat claims the DEPLOY slot, bumps the
version, writes player-language release notes, deploys, and then **verifies three ways**,
because a healthy container is not evidence the new code is being served:

1. **Build provenance** — the container was created *after* the tip commit.
2. **Markers in the container's own asset directory** — user-facing strings, never function
   names (minification renames them) and never the entry bundle (code-splitting moves them).
3. **A pre-existing marker still present** — so a build that ships your rows while dropping a
   predecessor's cannot read as success.

Then the loop closes with whoever asked:

> The player's report arrived at 09:49. The ordering fix, its replay-parity companion, and a
> forecast warning shipped that evening. `UPDATE` the queue row first, `NOTIFY` second — the
> bot's handler re-reads the row and silently no-ops if the status isn't committed yet.

**Deploy safety:** before shipping, the seat checked for live battles. The only in-progress
one was eight days stale — abandoned, not a player mid-fight.

---

## 6 · Redistributing

The moment a train ships, the seat re-assigns from the queue it has been accumulating. By
end of session the board carried **sixteen rows filed from verifier findings and sweep
results** — none of them invented, every one traceable to evidence.

Redistribution also honours dependencies. When one row's fix made another row's fix
*compile*, the seat sequenced them (`ORCE-15 → ORCE-24`) rather than running them in
parallel.

### The background sweep

With the trains moving, one sibling ran the full integration sweep — the thing nobody does
per-change because it takes hours. It found **four suites red on main**, none from that day's
work: red for **37 days**, **34 days**, **10 days**, and one asserting a value the code
*cannot produce* — an off-by-one in the test's own comment, wrong since at most **71 days**.

Two methodology rules came out of it, both now in the kit:

- **Pin the sweep to a SHA in its own worktree.** The shared checkout moved under the sweep
  as the seat and siblings committed; chunks measured against different trees make
  attribution — the entire deliverable — worthless.
- **Replay your scoping patterns against the full file list before claiming coverage.** One
  suite matched no chunk pattern and had never run. The report would have said "149/149"
  having run 148, and **the omission is invisible from inside the chunking.**

Equally valuable: the sweep **falsified both of the seat's hypotheses** — a production data
change it had made broke nothing across 39 suites, and a client change broke nothing across
all 21 replay suites. That is what let the seat ship without hedging.

## 7 · Rows the seat killed

Two rows were closed without building anything, and both closures were good outcomes:

- One claimed a defect affecting un-migrated rows. The builder queried production: **zero
  rows, unreachable from every write path.** The row existed because two code comments
  described a migration in the *future tense* — it had shipped five weeks earlier, and an
  audit believed the comment over the data.
- One suspected an accrual bug. The builder proved the number correct and, better, produced
  an invariant that *would* have caught a real bug and measured it across the whole
  population: **zero violations in 91 rows.**

**Require the population count before the build.** "Zero" is a finding — say it out loud on
the row so nobody re-files it.

## 8 · What the seat got wrong

Recorded because a worked example that only shows the system succeeding is not useful:

1. **Wrote an unverified premise into a brief** (§1). Caught pre-build by the sibling.
2. **Illustrated a "find every site" requirement with three examples** — the builder guarded
   exactly those three; the real population was eight. An illustration inside a requirement
   is read as the requirement.
3. **Stripped a sibling's hedges twice** — "I ran no sweep" became a causal claim; "a small
   piece of evidence" became "a natural experiment." Both retracted, both by the sibling.
4. **Issued an instruction the toolchain violates automatically** ("don't clean the shared
   containers" — the gate cleans them at stage 1). The fix was an env knob, not a rule.
5. **Stacked three concurrent gate runs**, one of which crashed under the load and produced a
   red that was not a red.
6. **Pushed from inside a worktree twice**, both no-ops.

Every one was caught. **Four were caught by a sibling correcting the seat** — which only
works if the seat responds by checking rather than defending. As Sib3 put it:

> "The cost of raising a correction is one message; the cost of being wrong is a row built on
> a false premise. That asymmetry is the mechanism, not anyone's virtue. And it only holds
> because you responded to all three by checking — a seat that argued back would have trained
> it out of me in an afternoon."

That is a design obligation on the seat, and it is written into the kit as one.

## The loop, condensed

```
orient → take the seat (banner, verified resume state, prefix)
   ↓
intake (human · task board · community queue · verifier findings)
   ↓
decompose → disjoint fences → assign (message + board row)  ──┐
   ↓                                                          │
builders work in isolated worktrees; report at phase          │
boundaries; correct the brief upward                          │
   ↓                                                          │
verify (contract-only, independent) ─── DEVIATES ──→ roundtrip┤
   ↓ PASS                                                     │
reconcile one row at a time → push → VERIFY THE PUSH          │
   ↓                                                          │
combination gate (foreground, unpiped, echo the tree)         │
   ↓                                                          │
deploy the train → verify live three ways → close the loop    │
   ↓                                                          │
log via the LOG slot → redistribute from findings ────────────┘
```

**One rule underneath all of it:** every green signal in this system means something narrower
than it appears. A passing summary is not a passing process. A clean tree is not a restored
tree. A successful push is not a landed commit. A guard that compares names cannot see types.
The orchestrator's real job is knowing which narrower thing each green actually means.
